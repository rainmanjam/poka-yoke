What you're doing wrong is a category error, not a phrasing problem: CLAUDE.md is prose, and prose to an agent is what Shingo would call rung zero — training, not a device. Capitals and repetition don't change the rung. It works ~90% of the time because the instruction is *near* the point of decision often enough, and fails the other 10% because of context compaction, subagents that never load CLAUDE.md, or the instruction simply losing salience over a long session. A rule an agent can forget, it will forget, at a rate you can't predict or budget for.

The fix is to move both rules off the rung-zero list and onto the tool boundary, where the harness — not the model — refuses the call before it runs.

**1. Deny rules in `.claude/settings.json`** (fast, catches the common spellings):

```jsonc
{
  "permissions": {
    "deny": [
      "Bash(git push --force:*)",
      "Bash(git push -f:*)",
      "Bash(git push --force-with-lease:*)",
      "Edit(./src/generated/**)",
      "Write(./src/generated/**)"
    ]
  }
}
```

**2. A hook for the part a pattern can't reach.** Both of your rules have a gap a plain deny list misses:
- Force-push has other spellings a careless or "helpful" agent can drift into — `git -c push.default=... push origin +main`, a wrapper script, an alias. String-matching `git push --force` won't catch all of them.
- `src/generated/` can be written without ever calling the Edit or Write tool — `sed -i`, `cat > src/generated/x.ts`, `cp`, a script the agent writes and runs. Those go through **Bash**, which the Edit/Write deny rules never see.

So this needs a `PreToolUse` hook on `Bash` that inspects the actual command string: regex for `push`+(`-f`|`--force`) anywhere in the arg list, and a check for any redirection/`sed -i`/`cp`/`mv` targeting `src/generated/`. That closes the gap the literal deny list leaves open.

**3. The deny message matters as much as the deny.** The agent reads whatever the hook returns and acts on it — a bare "denied" just prompts a workaround. Something like:

> Blocked: this command writes to `src/generated/`, which is regenerated by `<your codegen command>` and never hand-edited. If the generator itself needs to change, edit its source and re-run it.

> Blocked: force-push rewrites shared history on `<branch>`. If you need to fix a bad commit, create a new commit instead, or ask the user to force-push themselves.

**4. Commit `.claude/settings.json`** (not `settings.local.json`) — otherwise the guardrail only exists on your machine, which is the same failure as writing it in CLAUDE.md, just one layer down.

**5. Prove it fires before trusting it.** An unverified hook is worse than none — it looks like protection and isn't. Concretely: try `git push --force` on a scratch branch and confirm the denial and its message appear; try a normal `git push` and confirm it's unaffected; try editing a file in `src/generated/` via Edit and via `sed -i`, confirm both denied; edit a normal source file, confirm it's untouched by the rule.
