## You're not doing anything wrong with the wording. The wording is the wrong tool.

In Shingo's terms, a line in CLAUDE.md — caps, repeated, bolded, whatever — is **rung 0: training**. Training degrades. Capitalizing it twice doesn't move it up a rung; it's still a thing the agent has to *remember* at the moment of action. The ~1-in-10 failure rate is exactly what you'd predict for training, and it has predictable causes none of which your phrasing can fix:

- **Context compaction** — long sessions get summarized; the rule can get compressed out.
- **Subagents** — spawned agents get a task prompt, and may never see CLAUDE.md at all.
- **Pressure** — a rejected push or a stubborn generated-file diff creates a local incentive to "just fix it"; that's when a remembered rule loses to the shortest path to "done."

Both of your rules are **irreversible** actions, which is precisely the category where the skill says only **rung 1 (Control — the action is impossible)** is acceptable. Stop writing instructions; install devices.

## Devices — what to install

### Force-push: deny at the tool boundary + deny at the server

`.claude/settings.json` (committed, so it applies to every teammate's agent, not just yours):

```jsonc
{
  "permissions": {
    "deny": [
      "Bash(git push --force:*)",
      "Bash(git push -f:*)",
      "Bash(git commit --no-verify:*)",
      "Edit(./src/generated/**)",
      "Write(./src/generated/**)"
    ]
  }
}
```

The deny is evaluated *before* the tool runs — it doesn't matter whether the agent remembers anything. But it's client-side, so also put **branch protection with force-push disabled** on the repo (GitHub → Settings → Branches, or a ruleset). That's the true Control rung: even an agent invoked from a different machine, or a human, physically cannot do it.

Two caveats from the skill worth knowing:
- Plain deny patterns are dumb about variants (`git push origin +main`, `--force-with-lease`, flags in a different order). The plugin's `guard_dangerous_commands.py` hook handles those with a regex that blocks `--force`/`-f` but deliberately *allows* `--force-with-lease`, and returns a reason message naming the alternative. **The message is the device** — a bare "denied" produces a creative workaround; a message saying *what to do instead* produces the right action.
- Decide whether you want `--force-with-lease` allowed at all. The shipped hook permits it. If "never force push" means never, add a deny for it too.

### `src/generated/`: deny + header + regeneration gate

Three layers, each catching what the previous one misses:

1. **Deny rule** (above) — blocks `Edit`/`Write` on the path. Note this does *not* stop `Bash(sed -i ...)` or the generator itself — which is correct, since the generator needs to write there.
2. **A header in every generated file**: `// GENERATED by <tool> from <source>. Do not edit — changes are overwritten. Edit <source> instead.` This is the one place prose works, because it's *at the point of action*, not in a file read once at session start — and it tells the agent the correct move (edit the source).
3. **A CI check** that re-runs the generator and fails on a diff. This is rung 2 (Warning) and catches every path the deny misses — Bash edits, subagents, other tools, humans.

## Then delete the lines from CLAUDE.md

Once the devices exist, the caps-lock rules are dead weight. Per the skill: what stays in CLAUDE.md should be *facts* ("`src/generated/` is produced by `pnpm codegen` from `schema/`"), not commands you hope get followed. The fact is actually more useful — it tells the agent where the real edit goes.
