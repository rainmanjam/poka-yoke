## Your two rules aren't the same hazard

| Rule | Reversibility | Right device |
|---|---|---|
| Never force-push | **Irreversible, outward-facing.** Rewrites shared history; a colleague's work is gone. | **Control**, at two boundaries |
| Never edit `src/generated/` | Cheap to undo — it's in git, and regeneration overwrites | Control is still free here, so take it |

**For force-push**, a local deny rule alone is not Control — it protects *this* agent on *this* machine. The server doesn't care. You want:

1. **Branch protection / `deny-force-push`** on the remote — the only rung-1 device, because it holds against every agent, every machine, and you.
2. A `Bash(git push --force:*)` deny in committed `.claude/settings.json` as the fast-feedback layer.

One real gap: pattern-based denies match `--force` and `-f`, but **not** `git push origin +main` — the refspec form is the same operation and slips through. Conditional hooks need that case, and this is precisely why untested hooks fail open while looking like protection.

**For `src/generated/`**: `Edit(./src/generated/**)` deny + a `DO NOT EDIT — generated by X` header in the files themselves. Two independent contacts, both free.
